# ColdStorageInventory 发版手册

> 适用范围：本仓（冻品冷库系统，InvenTree fork）的版本发布与数据保护流程。
> 本项目目前是**单机单实例**运行：开发与日常经营共用一台 Windows 机器、同一个 SQLite 库。
> 原则：**经营数据是命根子。发布先保数据，再换代码；每一步可回滚。**

---

## 0. 部署拓扑现状

| 项 | 现状 |
| --- | --- |
| 运行环境 | Windows 本机（AMD Ryzen 9 / RTX 3060），无 Linux 服务器、无 Docker |
| 后端 | Django `runserver` / `invoke dev.server`，`http://127.0.0.1:8000` |
| 前端 | Vite dev server `http://127.0.0.1:5173/web/`；生产形态用 `yarn build` 产物 |
| 数据库 | SQLite：`config/data/db.sqlite3`（gitignored） |
| 媒体 | `config/data/media/`（gitignored） |
| 配置 | `config/config.yaml`（gitignored，含 secret_key 与数据库路径） |
| 上游官方 Docker 部署 | 本仓**未使用**；仓库内无 `docker/` 目录（上游后续提交可能带来，见 §六） |

> 之前项目的"双环境（dev/deploy）+ docker load"流程**不适用**本仓，仅作未来迁移 Linux/Docker 时的思路参考，本文档不保留其细节。

## 一、发布方式选择

| 场景 | 方式 |
| --- | --- |
| 日常开发 | `scripts\start-dev.bat` 一键启动（热更新），无需发版 |
| 改了后端依赖/迁移 | 重启后端 + `invoke migrate`，见 §二 |
| 改了前端代码要"固定版本" | §三：打 tag + 记录 |
| 数据库结构变更上线前 | §二 + §五 先备份验证 |
| 未来迁到服务器/客户机 | §六 |

## 二、标准发布步骤（当前单机形态）

### 步骤 1 · 发布前检查

```text
[ ] git status 干净，所有改动已按 land-main-workflow.md 合入 master
[ ] 协作规范第 9 节验证合同全绿（ruff / invoke test --keepdb / yarn build / yarn harness）
[ ] 确认本次改动不涉及账单 append-only 红线或已过门禁
```

### 步骤 2 · 备份（不可跳过）

```powershell
# 数据库 + 配置 + 媒体一起备份，目录带日期
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
robocopy config\data "backup\$stamp\db" /E
copy config\config.yaml "backup\$stamp\config.yaml"
```

同时验证备份可恢复：确认 `backup\$stamp\db\db.sqlite3` 存在且大小合理（>0 且与近期规模一致）。

### 步骤 3 · 应用代码与迁移

```powershell
# 代码更新后
invoke migrate          # 应用数据库迁移（改过 models 时必有输出，记下迁移名）
invoke update           # 如上游同步带来依赖/静态资源变更，按 tasks.py 提示执行
```

### 步骤 4 · 重启与冒烟

```powershell
scripts\start-dev.bat -Restart    # 或手动重启两个服务窗口
```

冒烟清单（按 `project_notes/cold_storage_workbench/current/20260704-冷库库存主流程使用说明.md`）：

```text
[ ] 登录正常
[ ] /cold-storage/ 工作台打开，默认入口跳转正常
[ ] 查库存：搜"大虾"能出多型号结果，卡片字段齐全
[ ] 新货入库：建一笔测试入库 → 卡片即时刷新 → 再撤销/扣回
[ ] 出库扣数正常，无负库存
[ ] （若本次涉及）出库单：新增 → 保存 → 下载照片按钮 → 历史单据不可改
```

### 步骤 5 · 记录版本

```bash
git tag -a release-<YYYYMMDD-HHmm> -m "发布说明：<本次内容>"
git push origin release-<YYYYMMDD-HHmm>
```

版本号格式：`release-<日期>-<时间>`（如 `release-20260704-1030`）。**不用** `:latest` / 浮动引用。

## 三、发版检查清单

```text
[ ] 步骤 1 检查全过；master 与 origin/master 一致
[ ] 步骤 2 备份完成且验证可读；config/ 未进备份之外的位置

[ ] git log 只含预期提交，无意外 merge / rebase 痕迹
```

## 四、回滚

### 代码回滚

```bash
# 回到上一个 release tag
git switch --detach release-20260701-0900   # 先验证该 tag 可用
# 确认后把 master 指回去（经 PR/明示流程，不悄悄 force push）
```

### 数据回滚（危险操作，先停服务）

```powershell
scripts\start-dev.bat  # 确认两窗口已停（或 -Restart 前手动关闭）
# 恢复：
copy backup\<stamp>\db\db.sqlite3 config\data\db.sqlite3
copy backup\<stamp>\config.yaml config\config.yaml
```

**红线**：回滚数据库会丢掉备份点之后的全部经营数据（新账单、新库存变动）。执行前必须与老板确认可接受范围；能只回滚代码就不要动数据。

### 迁移回滚

```bash
# 单个迁移的回滚（仅当该迁移是本次发布引入且未产生不可逆数据变换）
cd src\backend\InvenTree
python manage.py migrate <app_label> <上一个迁移名>
```

涉及数据变换（删列、改类型）的迁移回滚前，先做步骤 2 级别备份。

## 五、数据库变更专项

| 场景 | 规则 |
| --- | --- |
| 新增 app / 新表 | 首选；不动上游表语义（协作规范 §6.2） |
| 给上游表加字段 | 走门禁：说明理由 → 老板确认 → migration + 测试 |
| 账单相关表 | **只能新增表/列**，不修改/删除历史列；append-only 在应用层与数据层同时成立 |
| 大批量数据修正 | 先备份 → 写成脚本 → 空跑预览 → 实际执行 → 核对计数 |

## 六、未来迁移到服务器（预案）

当需要脱离本机（如放到店里稳定机器）时：

1. **环境**：Linux + Docker Compose（上游 InvenTree 自带 `docker-compose.yml` 体系，随上游同步会带回 `docker/` 目录，届时以**上游官方部署文档**为准，不在本文展开）。
2. **数据搬迁**：SQLite → PostgreSQL（InvenTree 官方支持，改 `config.yaml` 的 `database.engine` + 数据迁移脚本）。搬迁前做 SQLite 全量备份，搬迁后冒烟 §二步骤 4 清单。
3. **双环境雏形**：同机双目录（`~/csiDeploy/` 与 `~/csiDev/`）+ 独立数据库 volume，预发验收后晋级；**生产库与经营数据永不与预发共库**。
4. 届时把本节展开为新文档，替换 §〇 的拓扑表。

## 七、常见问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 前端起不来，5173 被占 | 上次 Vite 未关 | `start-dev.ps1 -Restart`；或按提示杀掉旧进程 |
| 后端 8000 被占 | 旧 runserver 残留 | 同上 |
| 登录后页面空白 | 前端依赖未装 | `cd src\frontend; yarn install` |
| 迁移报错"table exists" | 库与迁移历史不一致 | **停**。先备份，再查 `python manage.py showmigrations`；不要伪造 migration 记录 |
| 库存卡片数据不刷新 | 后端进程是旧代码 | 重启后端窗口 |
| 中文显示乱码 | 终端编码 | 脚本已设 `chcp 65001`；手动窗口确认 UTF-8 |
