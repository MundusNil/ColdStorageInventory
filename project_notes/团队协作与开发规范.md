# 团队协作与开发规范 · ColdStorageInventory（冻品冷库系统）

> 适用范围：本仓单机单仓（Django 后端 + React 前端，基于 InvenTree 二次改造）。
> 读者：本项目开发者（目前就是老板本人）与协助开发的 AI 编程助手。
> 目标：在不破坏上游 InvenTree 底座、不丢失冷库业务数据的前提下，完成一次可验证、可回滚的改动。

- **规则不清楚**：需求文档 → 上游 CONTRIBUTING.md → 本规范 → 停下问老板。不能用默认值代替业务决定。

## 1. 一句话原则

> **上游 InvenTree 是底座不是对手；业务规则要有权威来源；经营数据只增不毁；每一步都要能回滚。**

本仓处理的是真实冻品批发经营，不是玩具 CRUD。一次看似很小的改动也可能影响库存数量、客户账单或现场作业：

- 能用测试、类型检查、构建验证的规则，不依赖口头记忆。
- 业务规则以 `project_notes/` 下的需求文档为准；上游 InvenTree 文档只解释"它怎么工作"，不决定"冷库怎么用"。
- 库存变动与账单必须可追溯、可恢复。
- 不确定时明确报出阻断项；不要实现一个"先跑起来"的替代方案并把它当成已确认行为。

## 2. 名词小词典

| 名词 | 大白话解释 |
| --- | --- |
| **上游（upstream）** | github.com/inventree/InvenTree，本项目基于它改造。只读：不推送、不提 PR、不开 issue。 |
| **本仓（origin）** | github.com/MundusNil/ColdStorageInventory。所有工作落这里，主分支 `master`。 |
| **冷库工作台** | `src/frontend/src/pages/cold-storage/`，面向老板/仓管/现场人员的中文界面，入口 `/cold-storage/`，也是项目首页默认跳转目标。 |
| **货品（Part）** | InvenTree 物料主档，对应冻品（如琵琶腿、大虾）及其型号规格。 |
| **库位（StockLocation）** | 货物存放位置。冷库按方位和上下层划分，规划约 8 个标准位置，名称以现场说法对齐为准（见总方案）。 |
| **库存批次（StockItem）** | 某货品一次入库的记录：数量、单位、生产日期、到期日期、进价。**生产日期 + 保质期 = 到期日期**。 |
| **入库** | 新货进库：选货品、填数量/型号/进价/入库时间，系统创建真实库存。 |
| **出库扣数** | 出货时从对应批次扣减数量。 |
| **账单 / 出库单** | 给客户的单据（抬头"海伟冻品"）：客户名称、电话、单据日期、商品明细（名称/单位/数量/单价/金额/备注）、固定温馨提示。**只增不改不删**，另设"是否结过账"状态。需求见 `project_notes/最紧急任务.md`。 |
| **原系统页面** | InvenTree 自带页面。保留给管理员查错、配置、处理复杂数据，不是废弃代码。 |
| **冗余代码** | 上游带来、当前业务用不上的功能。**暂不删除**（业务做完前可能用到），处置规则见 §6.3。 |
| **harness** | 现有检查设施：前端 `src/frontend/scripts/harness.mjs`（中文硬编码、包管理规约）+ 后端 pytest。 |
| **secret** | secret_key、数据库文件、客户电话等敏感信息。只在 `config/config.yaml`、`config/data/` 与环境变量里，不进 git、日志、文档、测试。 |

## 3. 项目长什么样

```text
ColdStorageInventory/                 # InvenTree 的 fork
├── src/backend/InvenTree/            # Django + DRF 后端（上游底座）
│   ├── InvenTree/                    # 核心配置：settings.py、urls.py、api.py
│   ├── part/ company/ stock/ order/ …# 上游业务模型（Part / Stock / Order 等）
│   └── config_template.yaml          # 配置模板（实际配置在根目录 config/config.yaml）
├── src/frontend/                     # React 19 + Mantine 9 + Vite + TS + Lingui（上游底座）
│   ├── src/pages/cold-storage/       # ★ 冷库工作台（本项目业务核心）
│   ├── src/router.tsx                # /cold-storage/ 路由注册处
│   ├── scripts/harness.mjs           # 中文硬编码 / 包管理规约检查
│   └── tests/                        # Playwright 行为测试
├── config/config.yaml                # ★ 实际配置（gitignored）：数据库、media_root
├── config/data/db.sqlite3            # ★ 实际经营数据库（SQLite，gitignored）
├── config/data/media/                # 上传媒体（gitignored）
├── scripts/start-dev.bat | .ps1      # 一键启动：后端 :8000 + 前端 :5173
├── project_notes/                    # 项目文档：总方案、本规范、SOP、发版手册、落主线
└── tasks.py                          # invoke 任务（setup-dev / migrate / test / update）
```

运行链路：

```text
浏览器 → Vite :5173（/web/）→ Django API :8000 → SQLite（config/data/db.sqlite3）
```

关键认知：

- 冷库业务目前主要在前端页面 + 既有库存 API 上实现，**尚无独立后端 app**；新增后端能力时优先新建 app/新表，不动上游表语义。
- 冷库工作台是并行新增的入口；原 InvenTree 页面保留并存。
- **不强制**走上游完整采购单/销售单/生产单流程（见总方案）；出库单是本项目自定义的轻量单据。
- 开发与日常经营共用这台 Windows 机器和同一个库，发版流程见发版手册。

### 工具链（固定，不得替换）

| 事项 | 用什么 | 禁止 |
| --- | --- | --- |
| 前端包管理 | yarn（仓库锁定 `yarn@1.22.22`） | npm / npx / pnpm |
| 前端源码 | TypeScript（`.ts` / `.tsx`） | 新增 `.js` / `.jsx` |
| 后端任务 | invoke（`tasks.py`） | 绕过任务跑裸命令做迁移/测试 |
| 后端静态检查 | ruff（check / format） | — |
| 前端文案 | Lingui（`yarn extract` → `yarn compile`） | 源码硬编码中文（harness 拦截） |
| 仓库搜索 | ripgrep | — |

## 4. 开发流程：按改动大小选档位

### 档位 1：琐碎改动

错别字、日志文案、不会改变接口或行为的样式调整。直接修改并验证，遵守分支与提交规则。

### 档位 2：Bug 修复

- 先复现，并增加覆盖根因的回归测试。
- 不得用吞异常、放宽校验或未说明的 fallback 掩盖问题。
- 涉及库存数量或账单数据的 bug：修复后核对真实数据是否需要补偿，并留下记录。

### 档位 3：新功能或边界变化

适用于新增业务能力、动数据库模型、改 API 合同、改权限、改单据结构、动上游核心文件。
按 SOP 走完整流程：澄清（grill）→ 规格（spec）→ 拆票（tickets）→ 逐票实现 → review → 落主线。
涉及 Django models / migrations / settings.yaml / API 语义时，先暂停等老板确认（SOP 门禁）。

## 5. 分支、提交与落主线

- 不直接更新远程 `master`。在非 `master` 分支开发，通过 PR 合入（本仓的"main"即 master，land-main-workflow.md 里写的 main 一律按此对应）。
- 一次 PR 只处理一个主题；**多主题必须拆分**。硬门槛（>20 文件 / ≥2 个 scope 即强制拆）与完整流程**只以** [land-main-workflow.md](land-main-workflow.md) 为准，本节不重复。
- 用户说"落主线"或"所有的都落主线"，指范围上全部合入，**不等于**允许塞进同一个 PR。
- 分支名：`feat/<主题>`、`fix/<主题>`、`chore/<主题>`、`docs/<主题>`；小写 ASCII kebab-case，不拆 `<scope>-<summary>`。
- 提交信息：中文、符合 Conventional Commits，如 `feat(cold-storage): 新增出库单打印`；标题必须说明实际动作与结果，不编造 issue 编号。
- PR 正文只写实际变化、价值、验证和限制；不合入未经人工 review 的 PR。

## 6. 代码怎么放

### 6.1 前端

- 冷库业务代码放 `src/frontend/src/pages/cold-storage/`；不把业务逻辑堆进 `App.tsx` 或上游页面目录。
- 组件不直接猜后端响应；复用上游 `src/frontend/lib/` 的 API 客户端与枚举（ApiEndpoints、ModelInformation、Roles）。
- 中文文案走 Lingui 流程（`yarn extract` → 翻译 → `yarn compile`），**源码不硬编码中文**，`yarn harness` 会拦截。
- UI 组件用 Mantine 9；跟随上游既有写法，不引入新组件库。

### 6.2 后端

- **不改上游模型字段语义**。新增能力优先新建 app / 新表 / 新端点，而不是改 InvenTree 现有表。
- 数据库变更只走 Django migrations；改模型前先写迁移，迁移文件与模型同提交。
- 修改上游核心文件（settings.py、api.py、urls.py 等）保持最小 diff，并在改动处加注释标明冷库自定义意图（如 `# ColdStorage customization:`），为上游同步冲突识别留标记。
- 权限沿用 InvenTree 角色体系（RolePermission）；新端点默认要求登录，公开端点需显式说明。

### 6.3 冗余代码处置（本仓特有红线）

- 上游带来的功能（生产单、BOM、构建/插件体系等）**当前一律不删**：业务做完之前可能用到，且删除会放大上游同步冲突面。
- 觉得碍事的处理方式：**不动代码**，在本文件或总方案里记录"该功能本项目不用"。
- 确实要删的：先列清单向老板确认，等冷库业务稳定后批量处理；删除本身作为独立 PR。

## 7. 安全与数据红线

### 7.1 密钥与配置

- `config/config.yaml`、`config/data/`（数据库 + 媒体）已被 gitignore，**永不解除**。
- 不把 secret_key、经营数据、真实客户电话写进代码、测试、提交、PR 或日志。
- 未配置的值必须明确失败，不得用假数据或示例账号继续运行。

### 7.2 业务数据（冷库的命根子）

- **账单/出库单只增不删不改**：历史单据禁止 UPDATE / DELETE，只能新增 + 结算状态标记。
- 库存数量变动必须可溯源（对应批次/操作记录），不做无来源直改。
- 任何会写数据库的操作（脚本、迁移、管理命令）先确认备份存在（发版手册 §三）。

### 7.3 删除与破坏性操作

- 删分支、清数据、删媒体前，先确认目标范围、恢复方式与停止条件。
- 不用 `reset --hard` 处理日常问题；AI 执行此类命令前必须说明目标与后果并获确认。

## 8. 与 AI 助手协作

AI 可以加速检索、实现和测试，但不拥有业务决定权。

- 先给权威来源：总方案、需求/使用说明、本规范、SOP、land-main-workflow.md。
- 要求 AI 先说明不确定项与验证方法；不接受"猜测可能是"的实现结论。
- AI 产出的改动至少检查四件事：是否泄漏 secret、是否改了上游语义、是否触碰账单红线、是否硬编码中文。
- 涉及时间逻辑（保质期/到期日期）的测试用可控时间，不做真实长等待。

### Harness 边界

- 前端规约用 `yarn harness`；行为测试走 `src/frontend/tests/`（Playwright）。
- 后端测试用 pytest（`invoke test`，加 `--keepdb` 复用测试库加速，详见 CONTRIBUTING.md）。
- 测试**不碰真实经营库** `config/data/db.sqlite3` 与 `config/data/media/`，不出网、不调真实外部服务。
- 不为套 SOP 新建空的 harness 目录，复用现有结构。

本仓不依赖上游 CI（`.github/workflows` 是 InvenTree 官方流水线，不为本仓门禁服务）。以下检查在本地完成，任何一项失败不得合入：

| 检查 | 命令 |
| --- | --- |
| 后端静态检查 | `ruff check src/backend/` |
| 后端测试 | `invoke test --keepdb`（参数详见 CONTRIBUTING.md） |

| 前端源码规约 | `yarn harness` |

修复 bug 必须附带回归测试；新流程必须覆盖失败与恢复路径。

## 11. 上游同步 SOP（fork 专项）

本仓 fork 自 inventree/InvenTree，上游仍在活跃更新。同步目的：**拿到上游修复，同时保住冷库自定义**。

**当前状态**（写文档时）：本地领先 40 个自有提交、落后上游 258 个提交；上次同步记录为 `chore: sync upstream master`。

**永远不变的规则**

1. `upstream` 只 fetch 不 push（已配置 `pushurl DISABLED`，不要改回来）。不给上游提 PR、不开 issue。
2. 同步 = 把 `upstream/master` **merge** 进本仓 `master`，保留双方历史。**不要 rebase 自己的历史**——自有提交已推送，rebase 会毁掉 origin。
3. 同步后必须全量跑第 9 节验证合同，并手工冒烟：登录、冷库工作台、查库存、入库、出库。

**标准步骤**

```bash
# 1. 看差距
git fetch upstream
git rev-list --left-right --count master...upstream/master   # 左=自有领先 右=落后
git log --oneline master..upstream/master | head -30         # 预览上游新提交

# 2. 工作树干净后，在同步分支上合并（大同步时必须建分支）
git switch -c chore/sync-upstream-YYYYMMDD
git merge upstream/master

# 3. 冲突处理原则
#    - 纯自有文件（.omp/、project_notes/、scripts/start-dev*、pages/cold-storage/）：保留本仓版本
#    - 上游文件中带 ColdStorage customization 标记的改动：两边意图逐段合并
#    - 拿不准的：列出冲突文件清单，停下问老板

# 4. 全量验证（第 9 节）+ 手工冒烟

# 5. 按 land-main-workflow.md 落入 master，打同步记录 tag
```

**节奏**：建议每 1~2 个月同步一次；拖得越久冲突面越大。当前积压 258 个提交，下次同步预计需要专门安排半天处理冲突。

## 12. 遇到问题怎么办

1. 先查：总方案 → 使用说明 → CONTRIBUTING.md → 本规范 → 上游官方文档（docs.inventree.org）。
2. 复现后再修：保留错误、日志与最小复现，不做连续猜测式改动。
3. 同一方向失败 2 次即停：读 `git diff`，用自己的话重述问题（SOP 熔断规则）。
4. 发现规范与现实冲突：先改文档再改代码，不让代码悄悄成为新真相。
